## Конкретні проблеми

1. **P0 · Перевірка походження моделі прив’язана до CLI.** У `provenance.code_sha256_lf` записані 11 файлів: `matching.py`, `adaptive_corrected.py`, `logistic_baseline.py`, `run_known_methods.py`, `run_experiment.py`, `audit_wdc.py`, `prepare_final_method.py`, `frozen_method_artifact.py`, `search_system.py`, `search_cli.py`, `product_catalog.py`. І loader corrected, і фінальний preflight звіряють весь список. Навіть редагування представлення JSON може зламати обидва шляхи. Серіалізовані Python-класи також залежать від імпортованих імен. Заміна хешів у старій конфігурації зруйнувала б перевірку походження. [Конфігурація](final_method/frozen_configuration.json) · [Loader](../frozen_method_artifact.py) · [Preflight](../final_evaluation.py)
2. **P0 · Байти відтворення залежать від checkout.** Локально `core.autocrlf=true`, репозиторій не містить `.gitattributes`. Порівняння з `git cat-file blob HEAD:<path>` дало збіг із маніфестами лише для **3/23** фінальних файлів і **5/9** файлів snapshot разом із прив’язаним результатом. Для всіх 24 розбіжностей нормалізація CRLF до LF дала однаковий вміст. Snapshot поєднує файли з різними потрібними EOL. Чистий `git status` сам по собі не засвідчує придатність робочої копії до побайтової перевірки. [Маніфест snapshot](../snapshots/adaptive_v1/manifest.json) · [Маніфест фінальних результатів](final_evaluation/artifact_manifest.json)
3. **P1 · CLI двічі формує пул для одного запиту.** `search_payload` створює `SearchEngine`, викликає `retrieve` для JSON, а потім `search`, який знову викликає `retrieve`. На кожен виклик `search_payload` також заново будується індекс. Сам рушій уже підтримує повторні запити без fit. Публічної операції ранжування переданого пулу немає. Це конкретна причина відокремити виконання запиту від серіалізації та надати evaluator доступ до того самого пулу. Виграш у часі не вимірювався. [Складання відповіді](../search_cli.py) · [Рушій](../search_system.py)
4. **P1 · Поточна інструкція запуску суперечить фінальним матеріалам.** README ще повідомляє про невиконаний TEST і можливість повного pytest без WDC. `docs/search_system/usage.md` перелічує лише Fixed/Renorm. Фактично CLI також підтримує corrected із перевіреним bundle. LR доступна через Python API з готовим extractor і моделлю; наявність LR у bundle не вмикає її в CLI. Історичні числа 432 і 483 стосуються попередніх етапів. Новий короткий блок актуального стану в README може виправити навігацію, зберігши походження старих записів. [README](../README.md) · [Підсумок виконання](final_evaluation/reproducibility.md)
5. **P2 · Дослідницькі скрипти імпортують службові функції один одного.** Наприклад, `final_evaluation.py` імпортує `_representation_metadata` з `run_known_methods.py`, `json_digest` з `prepare_final_method.py` і форматування таблиці зі `study_method_selection.py`. Є кілька реалізацій хешування, серед яких побайтові й LF-нормалізовані. Для нового evaluator залежність від усього runner заради утиліти ускладнила б перевірку протоколу. Історичний код має чинних споживачів і зафіксовані хеші; його масове об’єднання не окупається.
6. **P2 · Зовні схожі функції мають різний контракт.** Старий `collect_offers` доповнює порожні поля повторного ID, тоді як WDC-імпортер відхиляє суперечливий запис, а FPV-імпортер відхиляє будь-який повтор ID. `tests/test_matching.py` викликає старі `collect_offers` та `search`. Для `as_pair` внутрішніх викликів не знайдено. Видалення не дає виграшу, співмірного з ризиком для зовнішнього виклику й хешу CLI. Історичний `matching.scores` потрібен `run_experiment.py`.

## Архітектура для наступних етапів

| Межа | Що використовувати та де проходить відповідальність |
|---|---|
| Каталог → пошук | Залишити `ProductOffer`, наявні імпортери та єдину проєкцію `offer_to_pair`. Ознаки походять із назви, опису, бренду та identifier із назви. Ціна, URL, FPV-характеристики й примітки доступні для відображення. Мітки пар і cluster ID залишаються поза каталогом пошуку. |
| Виконання запиту | Розвивати наявний `SearchEngine`. Цільова операція приймає ID і ліміти та повертає кандидатів і ранжовані результати за один відбір. Ранжування готового пулу використовує один і той самий код для звичайного пошуку й evaluator. Публічні `retrieve` та `search` зберігають сигнатури, результати й поведінку помилок. |
| Представлення | CLI серіалізує результат у чинну схему та текст. Майбутній локальний UI використовує той самий рушій, підготовлений для каталогу й методу, і дані `SearchResult.offer`. Вибір реальної пропозиції за фрагментом назви, порівняння полів, перевірка URL для клікабельних посилань і показ лише доступних методів — окремі вимоги UI. Зараз є точний запит за ID. |
| Оцінювання | Окремий evaluator володіє запитами, qrels і метриками, викликає retrieval, зберігає впорядкований пул з оцінками й передає його кожному сумісному ранжувальнику. Порядок retrieval сам є базовим порядком для порівняння. Формули і перевірки frozen-моделі залишаються в наявних модулях. |

Математичний контракт охоплює нормалізацію NFKC/casefold і пробілів, символьні n-грами 2–4, правила fit/дедуплікації й відкидання порожніх документів. Retrieval використовує назви поточного каталогу. Fixed/Renorm використовують каталогові ознаки; corrected і LR — власний TRAIN-fitted extractor. Спільні параметри TF-IDF не є достатньою підставою для взаємозаміни словників або IDF.

Фільтр джерела застосовується до зрізу `candidate_k`. Власна пропозиція й нульове перекриття виключаються. Кандидати впорядковуються за спаданням retrieval score, далі за зростанням рядкового ID. Результати — за спаданням similarity, retrieval score, далі за зростанням ID. Типові значення — `renorm`, 20 кандидатів, 5 результатів. Відсутня окрема ознака стає JSON `null`; спостережуваний нуль зберігає значення 0. Для зовнішнього scorer цілий блок діагностики може дорівнювати `null`.

## Межа наступного дослідження

Збережений WDC TEST охопив шість методів на 4500 готових парах. Його результати вже переглянуто. Повнота retrieval та якість наскрізного ранжування залишаються невстановленими. Для FPV в актуальній черзі 7 рядків зі статусом `pending` і 0 підтверджених міток. [Фінальний звіт](final_evaluation/test_results.md) · [Обмеження](final_evaluation/limitations.md) · [Аудит FPV](fpv_dataset_audit.md)

Перед окремо погодженим evaluator потрібно перевірити на TRAIN/validation однозначність offer ID і cluster ID, узгодженість pair labels, перетини split, повноту множини релевантних пропозицій, singleton-запити та доступність позитивів після фільтрації. За неповних суджень слід документувати межу вимірюваної повноти. Протокол фіксує запити, каталог, фільтри, глибини, хеші й однакові пули. Candidate Recall@K належить етапу відбору; Hit@K і MRR@K — кінцевому порядку з явно заданим знаменником і обліком порожніх відповідей. Історичний `apply_missingness` змінює матрицю готових пар. Для наскрізного сценарію маска має застосовуватися до пропозицій **до побудови індексу**, з однаковими seeds і сценаріями для всіх методів.

Цей аудит фіксує перевірки поточної реалізації. Продуктивність, повнота qrels і переносність чистого checkout залишаються відкритими питаннями. Першими до погодження пропонуються кроки 1–3. Рішення про зміну захищених модулів належить до кроку 4.
