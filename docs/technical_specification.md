# Технічне завдання

## Інтелектуальна система адаптивного пошуку товарних пропозицій

- **Статус:** робоча специфікація, версія 0.1
- **Дата:** 22.11.2026
- **Репозиторій:** https://github.com/m1b0mb0/adaptive-product-matching
- **Середовище розробки:** Python 3.12.10, Windows, VS Code / Codex
- **Призначення:** програмна частина магістерської роботи зі спеціальності 126 «Інформаційні системи та технології», ОП «Інтелектуальні системи та технології».

> Цей документ визначає цільовий стан системи, а не стверджує, що всі функції вже реалізовано. Перед будь-якими змінами агент перевіряє фактичний стан локального коду, тестів, даних і документації. Технічні рішення можуть уточнюватися за результатами аудиту із фіксацією причин.

## 1. Мета, предмет і межі

### 1.1. Мета системи

Надати користувачеві можливість знаходити й порівнювати товарні пропозиції, отримані з різних вебджерел і збережені в локальному каталозі, застосовуючи текстове формування кандидатів та атрибутивне ранжування. Вивчити можливості й обмеження відомих методів за неповних характеристик товарів.

### 1.2. Основний сценарій

Користувач знаходить у локальному каталозі початкову товарну пропозицію за назвою чи іншим доступним ідентифікатором, обирає її та отримує впорядкований перелік потенційно відповідних пропозицій. Можна переглянути характеристики, джерела, доступні оцінки й порівняти товари. Базовий режим — **query-by-example**. Текстове поле вибору початкового товару **не означає** реалізацію універсального пошуку довільного товару в інтернеті.

### 1.3. Межі

- Система працює з **локально імпортованими пропозиціями**, а не з живим скрапінгом сайтів під час запиту.
- Дослідницький прототип не є маркетплейсом, системою замовлень, моніторингу цін або промисловим пошуковим кластером.
- Оцінки подібності — виходи алгоритмів, а не калібровані ймовірності ідентичності товарів.
- Відсутні дані не домислюються. Метадані FPV не перетворюються на scoring features без окремого обґрунтованого рішення.
- Якість зіставлення відомих пар не прирівнюється до якості формування кандидатів чи наскрізного пошуку.

## 2. Вихідний стан, який необхідно перевірити

За попереднім описом існують: `matching.py`, `adaptive_corrected.py`, `logistic_baseline.py`, `product_catalog.py`, `search_system.py`, `search_cli.py`, `fpv_dataset.py`, дослідницькі скрипти, тести та документація. Реалізовано імпорт WDC Products/FPV, `ProductOffer`, нормалізацію, title-only TF-IDF retrieval, pairwise scoring, ранжування, пошук за `offer_id`, CLI/JSON, фільтр джерел за відомих значень.

Відомі експериментальні методи: TF-IDF, Fixed Weighted, Renormalization, Adaptive v1, Logistic Regression, Adaptive corrected. Фінальне незалежне **pairwise** оцінювання WDC TEST уже проводилось; переглянутий TEST не можна використовувати для підбору нових параметрів та представляти як незалежне підтвердження їх якості. У публічному README можливі застарілі твердження: локальні файли та frozen-артефакти мають пріоритет лише після перевірки їх походження й узгодженості.

**До початку змін:** провести інвентаризацію модулів, імпортів, точок входу, залежностей, тестів, наявних локальних файлів, схеми даних, користувацьких сценаріїв та ризиків для відтворюваності. Задокументувати підтверджені факти та розбіжності.

## 4. Вимоги до користувацького інтерфейсу

### 4.1. Основний екран

1. Назва системи та коротке пояснення: пошук **аналогічних пропозицій у завантаженому каталозі**, без претензії на live web search.
2. Вибір доступного каталогу (наприклад, WDC / FPV), якщо файли локально присутні; стан завантаження та кількість пропозицій.
3. Поле пошуку *початкового товару* за назвою/частиною назви і можливість точного вибору `offer_id`.
4. Візуальний блок вибраної пропозиції з підтвердженими полями.
5. Керування `candidate_k`, `top_k`, доступним методом, фільтром джерел; значення за замовчуванням документуються.
6. Кнопка виконання пошуку, індикація процесу та обробка пустої видачі.
7. Картки результатів із порядковим номером, назвою, джерелом, наявними характеристиками й score. Уніфіковане відображення пропусків як «Немає даних».
8. Перегляд пари товарів у таблиці порівняння. За потреби — розкриття технічних scoring details.

### 4.2. Візуальні вимоги

Охайна сучасна вебсторінка, послідовна ієрархія, контраст, адаптивна сітка, видимі активні стани, підказки, доступні назви елементів, керування клавіатурою. Не покладатися на колір як єдиний спосіб розрізнення станів. Не вигадувати фотографії товарів, ціни, наявність на складі, рейтинг, магазин або адресу сторінки. Якщо оригінального зображення немає, використати нейтральний placeholder.

### 4.3. Рекомендована реалізація

Після аудиту обрати **один** простий стек. Початковий рекомендований варіант: **FastAPI + Jinja2 + мінімальний CSS/JavaScript** з локальним сервером і server-rendered сторінками. Це дає нормальний користувацький вебінтерфейс без окремого SPA, Node.js або великої фронтенд-інфраструктури. Якщо існуючі залежності чи дослідницькі обмеження переконливо роблять Streamlit кращим, допустимо обрати його у короткому ADR із поясненням причин. Архітектуру UI не змішувати з функціями scoring. Окремий REST API не є обов'язковим, якщо не потрібен для обраної реалізації.

## 5. Архітектурні принципи

Модулі за роллю (точні назви/пакети визначити **після** інвентаризації):

- **Domain / catalog:** модель `ProductOffer`, валідація, джерела даних.
- **Matching / retrieval:** наявна нормалізація, витягування ознак, кандидати, скорери.
- **Application search service:** orchestration отримання кандидатів, ранжування і підготовка результатів; спільний для CLI та UI.
- **Evaluation:** ізольовані gold labels, qrels, метрики, протоколи, звіти; жодні мітки не доступні production search code.
- **Presentation:** CLI/JSON і вебінтерфейс — тонкі адаптери над спільним сервісом.
- **Research/legacy scripts:** експериментальні скрипти, артефакти, протоколи й історичні результати зберігаються окремо від користувацького коду.

Не створювати «чисту архітектуру» з десятками абстракцій лише заради структури. Кожне нове розділення повинно усувати реальне дублювання, ризик або складність тестування. Не перейменовувати/переміщати все одночасно; зберігати сумісність або явно документувати міграцію.

## 6. Вимоги до оцінювання

### 6.1. Перевірка даних до оцінювання

- Окремо проаудитувати TRAIN/validation: унікальність `offer_id`, однозначність кластерів, повноту відомих релевантних множин, singleton-кластери, суперечності pair labels і cluster IDs, перетини між splits.
- Не припускати, що всі релевантні пропозиції відомі лише тому, що є `cluster_id`; підтвердити семантику кластерів і повноту каталогу.
- Визначити критерії включення запитів до метрик та обробку запитів без доступних позитивних відповідників.
- `cluster_id`, `label` і qrels повинні бути недоступні ретриверу та ранжуванню.

### 6.2. Протокол

- До експериментів зафіксувати каталог, список запитів, кандидатні глибини, `top_k`, алгоритми, конфігурації, політику фільтрації джерел, seeds і хеші даних/артефактів.
- Candidate Recall@K обчислювати по відомих релевантних пропозиціях **лише там, де повнота gold підтверджена**; інакше використовувати обмежені метрики та явно позначати incomplete judgments.
- На другому етапі однаковий пул кандидатів для TF-IDF порядку, Fixed, Renormalization та інших сумісних методів; порівняння робити для тих самих запитів.
- Вказувати Hit@K, MRR@K; nDCG@K і Precision@K лише коли їх інтерпретація коректна для gold labels. Подаються також частка порожніх відповідей і кількість оцінених запитів.
- Відрізняти unsupervised побудову представлень для поточного каталогу від frozen-представлень, підготовлених для попередніх pairwise-експериментів.
- Відтворювати/звіряти результати з наявними звітами, **не** змінювати історичні файли результатів і не називати переглянутий TEST незалежною оцінкою після нових рішень.

### 6.3. Вплив пропусків

За наявності валідної розмітки застосувати визначені заздалегідь сценарії маскування до товарних пропозицій до побудови retrieval та scoring; однакові маски між методами, детерміновані seeds, окремий звіт. Не використовувати неперевірені FPV-пари як основний числовий benchmark.

## 8. План реалізації та критерії завершення

### Фаза 0 — Baseline, аудит і рішення щодо структури

Перевірити стан робочої директорії, тести, імпорти, документацію та залежності. Зафіксувати команду відтворення. Визначити архітектурні проблеми з доказами і пріоритетами; не підміняти аудит автоматичним масовим перейменуванням.

**Done:** є короткий audit/report + plan, baseline tests і список охоронних regression tests; не втрачено незакомічених змін.

### Фаза 1 — Контрольований рефакторинг

Поетапно розділити домен, retrieval/ranking, application service та CLI там, де це обґрунтовано. Додати characterization tests для існуючої поведінки. Не змінювати математику й historical scripts. Виконувати окремий коміт на кожен логічний крок.

**Done:** тести проходять, збережена функціональна й числова поведінка, розбіжності пояснені, нова структура задокументована.

### Фаза 2 — Evaluation readiness та evaluator

Перевірити qrels на локальних TRAIN/validation, зафіксувати протокол, реалізувати окремі candidate/ranking metrics і unit-тести з ручними прикладами. Експерименти виконувати лише після узгодження протоколу.

**Done:** підтверджена валідність розмітки, перевірені обчислення, reproducible reports.

### Фаза 3 — Вебінтерфейс

Погодити єдиний стек, реалізувати пошук початкового товару в локальному каталозі, параметри, результати, порівняння, обробку пропусків та помилок. UI викликає спільний сервіс, не дублює алгоритми.

**Done:** користувач проходить повний сценарій у браузері; CLI/JSON не зламані; є тести й інструкція запуску.

### Фаза 4 — Фінальні дослідження і демонстрація

Провести зафіксовані експерименти та аналіз помилок, за потреби missingness stress-test, зафіксувати обмеження. Узгодити текст магістерської з реальною реалізацією.

**Done:** відтворюваність, прозоре походження чисел, контрольований демонстраційний сценарій та актуальна документація.

## 9. Не входить до обов'язкового обсягу

Live scraping, платіжні функції, реєстрація, персоналізація, ML training у UI, складна мікросервісна архітектура, спеціалізовані ANN/векторні бази, довільні LLM-моделі, оптимізація великого продакшн-каталогу, доповнення невідомих атрибутів через здогадки.

## 10. Контроль змін

Рішення, що впливають на формули, preprocessing, ознаки, джерела релевантності, splits, модельні артефакти або протокол тестування, вважаються **змінами дослідження**, а не звичайним рефакторингом. Для них необхідні окреме обґрунтування, план тестування та погодження. Ця специфікація оновлюється окремими документованими змінами із зазначенням статусу реалізації.
